# Dynamic badges

A static badge says what you hoped was true when you wrote it. A dynamic badge
says what CI proved this morning. Add them in this order.

## 1. Run something in CI first

Badges render only after the workflow has run once **on the default branch**.
Wire the workflow first; decorate second.

Reuse the kit's workflow from another repository:

```yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:
jobs:
  test:
    uses: aadisthunder/readme-forge/.github/workflows/reusable-node-ci.yml@main
    with:
      node-version: "20"
      coverage: false
```

## 2. Badge snippets that work

Replace `OWNER` and `REPO`. Keep at most four above the fold.

## 3. Coverage without a token

Codecov is the common choice, but tokens are a common source of failed runs.
Token-free alternatives:

- Upload `coverage/` as a workflow artifact and link it from the README.
- Use a shields.io endpoint badge reading a `coverage.json` in a `badges`
  branch generated by CI.

If you do use Codecov: add `CODECOV_TOKEN` in repository secrets, pass it via
`secrets:` to the reusable workflow, and confirm the first upload succeeded
before adding the badge.

## 4. Honesty checklist

- [ ] Each badge links somewhere useful (not to the badge image alone).
- [ ] CI badge points at a workflow that actually runs on `main`.
- [ ] No badge for a metric the project does not track.
- [ ] Static badges (like "PRs welcome") stay, but they never outnumber
      dynamic ones above the fold.
- [ ] Badge row renders on one line on mobile (test at 400px).

## 5. Per-repository quick plans

| Repository | First three badges |
| :--- | :--- |
| A static site (College-ERP) | CI, License, Deploy |
| A client-side app with tests (Bravo) | CI, Tests count, License |
| A full-stack app with an eval suite (pragati) | CI, Coverage, Reproducible eval |
